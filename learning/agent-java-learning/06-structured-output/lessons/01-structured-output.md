# 第 3 课：Structured Output 与双层校验

## 为什么学习

前两课模型返回的是**给人看的文本**。第 1 课总结一句话、第 2 课真实调用，拿到的都是字符串——人读得懂，程序做不了什么。

这一课要让模型返回**给程序执行的数据**：

```text
第 1 课：「北侧新增一台雷达，东南角部署两台摄像头。」   → 只能显示给用户
第 3 课：{"operation":"create","deviceType":"radar",...} → 程序可以直接执行
```

这是从「聊天机器人」转向「Agent 应用」的分界线。Agent 之所以能做事，就是因为它的输出是结构化的、可执行的。

但一旦输出可执行，风险也来了。模型输出 `{"operation":"delete","targetId":"fence-main"}`，JSON 完全合法，程序照做——用户的关键设备就被删了。

所以本课的核心不是「怎么让模型输出 JSON」，而是**怎么在执行之前把它拦住**。

**本课暂时不解决**：Tool Calling（模型主动决定调哪个工具）、多轮对话、真正执行操作。这些分别在阶段 6、7 展开。本课只到「生成预览」为止。

## 核心结论：结构正确 ≠ 业务合法

这是整课最重要的一句话。看这个输入：

```json
{"operation":"delete","targetId":"radar-99","reason":"用户要求删除雷达"}
```

它的**结构**毫无问题：字段齐全、类型正确、搭配合规。任何 JSON Schema 校验都会放行。

但如果场景里根本没有 `radar-99`，这个操作就是错的。判断这一点，必须对照**真实场景状态**——而 Schema 校验只能看 JSON 本身。

所以校验必须分成两层：

| | 第一层：结构校验 | 第二层：业务校验 |
|---|---|---|
| 类 | `OperationSchemaValidator` | `SceneBusinessValidator` |
| 回答 | 字段搭配对不对 | 这件事现在能不能做 |
| 依赖 | 只看操作对象本身 | 需要场景快照 |
| 是否纯函数 | 是 | 否 |
| 结论是否随时间变化 | 不会 | 会 |

分层的收益很具体：第一层是纯函数，测试不用准备任何环境；换一个场景（不同边界、不同设备）时，第一层的规则和测试完全不用改。

## 完整链路：四步

```text
自然语言指令
    ↓ 第 1 步：调模型（temperature=0）
模型返回的文本（可能带围栏、可能夹解释、可能被截断）
    ↓ 第 2 步：OperationJsonParser —— 提取 JSON、检查字段类型
SceneOperation（结构上是个对象了）
    ↓ 第 3 步：OperationSchemaValidator —— 检查字段搭配
SceneOperation（字段搭配也对了）
    ↓ 第 4 步：SceneBusinessValidator —— 对照真实场景
OperationPreview（只是「将会发生什么」的说明）
    ↓ 等用户确认……（本课到此为止）
```

注意最后一步：**通过全部校验的产物是预览，不是已执行的修改**。

## 为什么不能直接 readValue

看起来只要 `mapper.readValue(text, SceneOperation.class)` 就行了。但模型输出**不是**干净的 JSON，真实环境至少三种情况：

```text
1. 包在代码围栏里    ```json\n{...}\n```
2. 前后有解释文字    好的，这是操作：{...}，希望有帮助！
3. 被截断           {"operation":"create","deviceType":"rad
```

第 1 种最常见，而且**即使系统提示明确说了「不要代码围栏」，模型还是会加**。这不是模型不听话——它的训练数据里 JSON 大多带着围栏。

直接 `readValue` 在这三种情况下都抛 Jackson 异常，而异常信息（`Unexpected character '`'`）对排查毫无帮助：你看不出是模型多说了话，还是输出被截断了。

### 宽容的边界在哪里

这里有个容易走偏的地方。解析层对**输出习惯**宽容，对**字段语义**绝不宽容：

| 宽容 | 不宽容 |
|---|---|
| 剥掉代码围栏 | 不猜字段名（`device` ≠ `deviceType`） |
| 忽略前后解释文字 | 不把字符串 `"10"` 转成数字 `10` |
| 枚举值大小写不敏感 | 不给缺失字段填默认值 |

前者是适配模型习惯，不改变语义。后者是**替模型掩盖错误**——一旦开始自动转换字符串数字，`"三十"` 也会被悄悄当成 0。

明确拒绝并把问题回传给模型，它下一轮就会输出正确格式。这比静默修正更安全。

## 三条容易被忽略的规则

### 未知字段要报错，不能静默忽略

模型会自信地编出不存在的字段：

```json
{"operation":"add", "device":"radar", "rotation":90}
```

`add`（应该是 `create`）、`device`（应该是 `deviceType`）、`rotation`（不存在）——三个都是幻觉。

静默忽略未知字段的后果：用户说「放一台朝北的雷达」，模型用 `rotation:90` 表达朝向，程序悄悄丢掉，设备朝向是默认值。用户以为设置成功了。

**未知字段是信号**，说明模型对契约的理解和你不一致。

### 多余字段同样是信号

`delete` 操作带了坐标，说明模型可能想表达 `move` 却选错了类型。静默丢掉坐标按 `delete` 执行——用户想移动设备，结果设备被删了。

### 全部错误一次报出

不是遇到第一个错误就返回。原因不是「用户体验好」，而是**省钱**：

每一轮都是一次真实的模型调用。只报第一个错误，模型改完再发，又撞上第二个——N 个错误要 N 轮才能修完，延迟和成本都是 N 倍。

这和 Spring 的 `@Valid` 一次返回全部字段错误是同一个道理（阶段 3 学过）。

## 危险操作要专门拦

`clear_all` 是本课最危险的操作：它**不需要任何参数**，所以结构上永远合法，Schema 层拦不住任何东西。

处理方式有三条：

1. **受保护设备**：场景里有受保护设备时，整体拒绝清空——而不是「删掉其余的」。用户说「清空」时很可能没意识到里面有关键设备，部分执行会产生一个用户没预期的中间状态，比直接拒绝更糟；
2. **预览必须标记破坏性**：`OperationPreview.isDestructive()` 让 UI 能加警告；
3. **预览而非执行**：这是最后一道防线。即使前面全被绕过，用户还有机会看一眼再点确认。

## 为什么必须把场景状态告诉模型

这一点很容易漏。如果模型不知道场景里有哪些设备，用户说「把那台雷达往东移」时它**只能编一个 id**——编出来的 id 一定过不了业务校验，这一轮 token 白花。

所以 system 消息里除了格式说明，还要带上当前场景状态：

```text
当前场景状态（请只操作真实存在的设备，不要虚构 id）：
  边界：200 x 200
  设备数：3 / 20
  设备清单：[cam-01, cam-02, fence-main]
  受保护设备（不可删除）：[fence-main]
```

关键理解：**业务校验能兜住模型的幻觉，但兜住不等于没有代价**。把真实清单给模型是从源头降低幻觉率，校验是最后一道防线，不是省掉上下文的理由。

代价也要说清楚：场景状态占输入 token，且随设备数量增长。设备成百上千时不能全量塞进 prompt，要改成先检索相关设备再给模型——这正是阶段 10 RAG 要解决的问题。

## temperature 设为 0

第 1 课总结任务用 0.2，这里用 0。区别在于：总结允许措辞变化，结构化输出不允许任何「创造性」。高温度会让模型在格式上发挥创意，直接降低解析成功率。

## 为什么手写校验而不用 JSON Schema 库

生产项目应该用成熟库（Java 常见的是 `networknt/json-schema-validator`）。本课手写是为了让你看清「Schema 校验」不神秘，就是这些条件判断——之后用库时，你知道它在替你做什么。

**手写的代价**要讲清楚：不支持嵌套对象、`oneOf`、正则约束，也不生成标准错误路径；字段一多就变成难维护的 `if` 堆。

还有一个更隐蔽的代价：**Schema 说明和校验代码是两处**，必须手动保持同步。写这一课时我加了坐标范围校验，就忘了同步更新发给模型的说明——用库可以直接把 Schema 序列化给模型，不会漏。

## 常见面试题

### 1. 为什么结构校验通过还需要业务校验？

**参考答案：**结构校验只能看 JSON 本身，判断字段是否齐全、类型是否正确。但「这台设备是否存在」「坐标是否在当前场景内」「这台设备是否受保护」都依赖运行时状态，JSON 里看不出来。模型输出 `{"operation":"delete","targetId":"radar-99"}` 结构完全合法，但如果场景里没有这台设备，操作就是错的。

**项目解决方案：**分成两层。`OperationSchemaValidator` 只检查字段搭配，是纯函数；`SceneBusinessValidator` 持有 `SceneSnapshot`，检查设备存在性、场景边界、容量上限和受保护设备。

**风险边界：**业务校验用的是快照，校验通过到真正执行之间场景可能已被别人改动。生产需要版本号做乐观锁，或在执行时重新校验。本课的快照没有版本号，属于已知简化。

### 2. 为什么未知字段要报错，而不是忽略？

**参考答案：**未知字段是信号，说明模型对契约的理解和你不一致。静默忽略会让理解偏差变成静默的数据错误——用户说「放一台朝北的雷达」，模型用 `rotation:90` 表达，程序悄悄丢掉，用户以为设置成功了，实际朝向是默认值。

**项目解决方案：**`OperationJsonParser.checkUnknownFields()` 把未知字段作为错误报出，并提示「模型可能在猜字段名」。多余字段同样报错：带坐标的 `delete` 很可能是模型想表达 `move`。

**风险边界：**严格模式会让模型的正常演进也报错。如果之后要支持新字段，必须同时更新校验和 Schema 说明——这是手写校验的维护负担，用库可以直接把 Schema 序列化给模型来缓解。

### 3. 为什么校验错误要一次全部返回？

**参考答案：**因为每一轮修正都是一次真实的模型调用。只报第一个错误，模型改完再发，又撞上第二个错误，N 个错误要 N 轮才能修完，延迟和成本都变成 N 倍。这和 Spring 的 `@Valid` 一次返回全部字段错误是同一个道理。

**项目解决方案：**`ValidationResult` 持有错误列表而不是单个错误；两层校验器都用 `List<String> errors` 收集完再返回。

**风险边界：**部分错误之间有依赖关系——`operation` 值非法时，后续字段的必填判断本身就没有意义，此时收集出的错误可能有噪音。真实项目要区分「致命错误」和「可继续收集的错误」。

### 4. 为什么校验通过后只生成预览，不直接执行？

**参考答案：**因为模型可能在**语义上**理解错，而这种错误任何自动校验都发现不了。用户说「把这些清理一下」，模型理解成清空整个场景，生成的操作结构合法、业务也合法（设备确实存在、确实可删），但完全不是用户的意思。预览加确认是唯一能拦住语义偏差的防线。

**项目解决方案：**`SceneBusinessValidator` 通过校验后返回 `OperationPreview`，只包含「将会发生什么」的描述和设备数量变化，没有任何写操作。破坏性操作额外标记 `isDestructive()`，确认文案带警告。

**风险边界：**预览依赖用户真的会看。用户习惯性点确认时这道防线就失效了，所以破坏性操作还需要更强的确认方式（二次输入设备名、冷却期），以及可回滚的执行机制。

### 5. `clear_all` 这种不需要参数的操作，危险在哪里？

**参考答案：**它结构上**永远合法**——没有参数就没有可校验的字段搭配，Schema 层拦不住任何东西。同时它的破坏力最大。所以它的全部防线都在业务层和确认环节。

**项目解决方案：**三条。场景含受保护设备时整体拒绝而不是部分执行；空场景时提示「本来就没有设备」；预览明确显示「设备数 3 → 0」并标记破坏性。

**风险边界：**「整体拒绝」意味着用户想清空非保护设备时也会被拒，需要逐台指定。这是刻意的取舍——不可逆操作宁可让用户多操作几步，也不要产生用户没预期的中间状态。

### 6. temperature 为什么设为 0？

**参考答案：**结构化输出不需要任何创造性。同样的指令应当得到同样的 JSON。温度越高，模型越可能在格式上「发挥」——加个字段、改个字段名、包上围栏——直接降低解析成功率。

**项目解决方案：**`SceneOperationService.callModel()` 用 `temperature=0.0`，和第 1 课总结任务的 0.2 形成对比：总结允许措辞变化，结构化输出不允许。

**风险边界：**temperature=0 不保证完全确定。同一模型版本、同样输入仍可能有细微差异（浮点计算顺序、服务端批处理），而且模型版本升级后输出可能变化。所以解析层的宽容和校验层的严格都不能省，这也是需要评估集的原因。
