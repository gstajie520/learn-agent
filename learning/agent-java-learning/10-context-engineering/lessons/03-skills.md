# 第 3 课：Skill 按需加载

## 这一课解决什么

前两课处理了两种上下文膨胀：第 1 课防「忘了目标」，第 2 课防「探索过程堆进主对话」。

还有第三种，而且最常见：**为了让 Agent 会做某件事，把大段操作规范塞进系统提示。**

十个领域各一份规范，系统提示就上万 token。而任何一次对话通常只用到其中一份——剩下九份每一轮都在付费，还稀释了模型对当前任务的注意力。

这一课的机制是两段式：

```text
系统提示里只放目录（每条一行）        ← 便宜，常驻
  - radar-troubleshooting：雷达离线时的排查顺序
  - camera-deploy：摄像头批量部署规范
        │
        │  模型自己判断这次要用哪一份
        ▼
load_skill(name="radar-troubleshooting")   ← 贵，按需
  → 返回那一份的完整正文
```

## 一、扫描阶段只读 frontmatter，不读正文

这是整个设计成立的前提，不是优化。

`SKILL.md` 的格式是 frontmatter + 正文：

```markdown
---
name: radar-troubleshooting
description: 雷达离线时的排查顺序
---

第一步：确认供电。
第二步：看网络链路。
（后面可能还有两千字）
```

`readFrontmatterOnly` 分块读，**遇到第二个 `---` 立刻返回**。一个 10 MB 的 SKILL.md 在扫描阶段只会被读掉前几百字节。

如果图省事写成 `Files.readAllBytes` 再切分，「扫描不读正文」就成了一句空话——正文已经进了内存，只是没拼进 prompt 而已。100 个 Skill 各 1 MB，启动时就是 100 MB 的无用读取。

`shouldReadOnlyFrontmatterDuringScan` 把这条钉死：造一个 frontmatter 合法、**正文是非法 UTF-8** 的文件。只读前半段的实现扫得过去，读全文的实现会当场炸。

## 二、目录里只有名称和描述

`SkillSummary` 只有两个字段。如果它多出一个 `body`，本课的机制就作废了——渲染目录时会顺手把正文一起拼进系统提示，而那正是「硬塞 Prompt」本身。

`shouldExposeCatalogWithoutBodies` 断言渲染结果里正文一个字都不出现。这条不会自己坏掉，但很容易被「顺手改一下」破坏，而且**破坏之后不报错**，只是系统提示悄悄变长。

## 三、双预算：条目数 + 字节数

只限条目数挡不住「100 个 Skill 每个写 500 字描述」；只限字节数会让目录在某个字节位置被切断，模型看到半行。

**只整条列出，绝不列一半。** 列半行的后果是模型看到残缺的名字，拿它去调 `load_skill` 必然失败，而且它看不懂为什么——它以为自己抄对了。

中文在这里是个坑：一个汉字 UTF-8 下 3 字节。按字符数算预算会严重超标，所以 `boundedCatalog` 用 `getBytes(UTF_8).length`，并且**把条目之间的换行符也算进预算**——否则「刚好卡在边界」时实际输出会超。

## 四、截断必须与机器无关

扫描用 `TreeMap` 按名称排序，不用文件系统的枚举顺序。

理由：如果按枚举顺序截断，同一份工作区在不同机器上留下的条目就不一样——「模型能用哪几个 Skill」取决于部署在哪台机器上。这种差异从日志里完全看不出来。

被预算截断的 Skill **仍然可以加载**：预算限制的是目录（进 prompt 的部分），不是能力。

## 五、name 必须等于目录名

一个叫 `deploy-guide` 的目录如果能声明自己是 `safe-readonly-guide`，模型以为加载的是后者，实际读到的是前者的正文。这是**身份冒充**。

所以两者不一致时硬失败，不取其中一个当准。

同理，**同名 Skill 必须硬失败，不能后来者覆盖**。允许覆盖的话，往工作区里塞一个同名 Skill 就能替换掉一个已有能力的正文，而模型看到的目录条目一字未变。

## 六、这一课引入了文件访问，所以要先建边界层

**这是本工程第一次碰文件系统。** 前面几个阶段刻意把教材的「文件 / shell 工作区」域换成了「场景 / 设备」域，代价是路径安全这一课一直没学到。阶段 9 后三课的机制本体都是文件系统，所以在这里把它补回来。

`WorkspaceGuard` 就是这道边界，第 4、5 课直接复用。

### 两道关，缺一不可

| | 词法关（不碰磁盘） | 物理关（必须碰磁盘） |
|---|---|---|
| 做什么 | 看字符串本身合不合法 | 解析真实路径，看它落在哪 |
| 能挡住 | 绝对路径、`..`、保留设备名、控制字符 | 符号链接 / junction 指向区外 |
| 挡不住 | 符号链接——字符串上完全合法 | 不存在的路径（还没创建时无法 realpath） |

**只做词法关不够**：`skills/demo` 这个字符串挑不出毛病，但它可以是一个指向 `C:\Windows` 的目录联接。

**只做物理关也不够**：要新建的文件还不存在，`toRealPath()` 直接抛异常，此时只能靠词法关。

### 词法关逐条

| 拒绝 | 不拒的后果 |
|---|---|
| 空串 / 全空白 | 拼出来就是工作区根，调用方以为拿到了子路径 |
| NUL 字符 | 底层 API 可能在 NUL 处截断，校验的和实际打开的不是同一个路径 |
| 绝对路径 | `Path.resolve` 遇到绝对路径**整段替换**，工作区根被彻底丢掉 |
| `..` 组件 | 典型逃逸：`../../.ssh/id_rsa` |
| Windows 保留设备名 | 打到设备而不是文件；写 `NUL` 数据静默消失，读 `CON` 会挂着等输入 |
| 尾随空格或点号 | Windows 静默剥掉它们，`"secret.txt "` 实际打开 `secret.txt` |
| 超长组件 | 不同文件系统截断长度不同，可能撞到别的文件 |

三个容易做错的细节：

1. **`..` 必须按组件判，不能用 `contains("..")`。** 后者会把 `my..file`、`..hidden` 这些合法名字全毙掉——而这类误伤最难发现，表现为「某些文件莫名读不了」。
2. **两种分隔符都要认，而且要在分段之前统一。** 模型分不清自己在什么系统上，`..\..\etc` 一定会出现。只按 `/` 分段的话，这整串会被当成**一个文件名**，那两个 `..` 根本进不了组件检查。
3. **保留设备名带扩展名的形式也要拒。** `CON.txt` 仍然指向设备，只做名字全等比较会放过它。

### 物理关：为什么每次加载都要重查

`loadSkill` 把扫描期做过的检查**全部重做一遍**，三层（Skill 根、Skill 目录、manifest）一层都不省。

因为扫描和加载之间隔着任意长的时间。这段时间里目录可以被换成一个指向工作区外的链接——这就是 **TOCTOU**（check 的时刻和 use 的时刻不是同一刻）。存下来的「已验证路径」在那一刻就过期了。

重新解析不能消灭这个窗口，但能把它压到最小。

还要重新核对「manifest 里的 name == 目录名」：SKILL.md 的**内容**也可能在扫描后被替换。只查路径不查内容，等于防住了目录被换、没防住文件被换。

`shouldRecheckPathOnLoadAfterDirectorySwapped` 真的做了这次替换：扫描成功、加载正常，然后把目录换成越界符号链接，再加载——必须失败。

### 包含性判断要按组件比

字符串前缀会把 `/work-evil` 判成在 `/work` 之内。前缀确实匹配上了，但那是两个完全不同的目录。攻击者只要在工作区旁边建一个名字以工作区名开头的目录，就能被判成「在区内」。

`Path.startsWith` 按组件比较，不犯这个错。

## 七、和教材的三处差异（如实记）

| 差异 | 教材 | 本实现 | 判断 |
|---|---|---|---|
| frontmatter 解析 | 真正的 YAML 解析器 | 手写，只认 `key: value` | 更严，方向安全 |
| 组件长度上限 | **没有做** | 255 字符 | Java 侧收紧 |
| 非法字符集 | 分两套（glob 模式允许 `*?`） | 一套，含 `*?` | 更严，因为本工程没有 glob 工具 |
| 工作区归属校验 | 比对 `ToolContext.workspace` | **做不了** | 见下 |

**手写解析器的代价要说清**：它比 YAML 更严格——嵌套结构、多行值、锚点、列表全部拒绝。这个方向是安全的（看不懂就拒绝，不会误解成别的意思），但如果哪天 frontmatter 需要支持嵌套字段，**必须换成真的 YAML 解析器**，不能在这里打补丁。手写解析器逐步长出对 YAML 子集的支持，是一条经典的出 bug 路径。

**工作区归属校验这条是真缺口**：教材的 handler 会解析 `ToolContext.workspace`，确认它和注册表扫描时用的是同一个工作区，防的是「拿 A 工作区的注册表去服务 B 工作区的会话」。Java 侧**做不了**——域重映射之后 `ToolContext` 携带的是 `identity` 和 `SceneSnapshot`，没有 workspace 字段，没有可比对的东西。当前工程里注册表与工作区是构造期绑定的，单会话下不会错配；但如果将来用在多租户场景，「注册表属于哪个工作区」必须有一个运行期可校验的载体。

## 八、和阶段 10 的 RAG 是两条路

都在回答「上下文放不下全部知识怎么办」。

- **Skill 是「少拿」**：知识在本地、边界清楚、按名字精确取，取到的是**完整一份**。
- **RAG 是「去找」**：知识在外部、按语义相似度召回，取到的是**若干片段**。

Skill 适合「操作规范」这种必须完整、不能只给片段的内容——半份部署规范比没有更危险。RAG 适合「资料库」这种没法预先命名的内容。

教材里只实现了 Skill（ch07），RAG 要自己写（阶段 10）。

## 常见面试题

**问：系统提示里应该放什么、不该放什么？**

放「每次都要遵守的规则」和「当前可用能力的目录」，不放「某些情况下才需要的详细规范」。判断标准是使用频率：一份规范十次对话里用一次，就该做成按需加载。常驻的代价是每一轮都付 token，而且内容越多，模型对当前任务的注意力越分散。

**问：按需加载的知识，怎么让模型知道有哪些可选？**

给它一个目录：每条只有名称和一行描述。描述的作用是让模型做「要不要加载」的判断，所以描述必须说清适用场景，而不是复述标题。目录本身要有预算上限，否则 Skill 一多，目录自己就变成了新的膨胀源。

**问：Skill 和 RAG 有什么区别，什么时候用哪个？**

Skill 是按名字精确取完整一份，适合操作规范这类必须完整的内容；RAG 是按语义召回若干片段，适合没法预先命名的资料库。关键差别在「片段是否可接受」——半份部署规范会让人照着做错，半段参考资料只是信息少一点。

**问：工具参数里带路径，你会怎么校验？**

两道关。词法关不碰磁盘，拒绝绝对路径、`..` 组件、保留设备名、控制字符；物理关解析真实路径，确认它仍在允许范围内。两道都要，因为符号链接在词法上完全合法，而要新建的文件在物理上还不存在。另外校验通过到真正读写之间有 TOCTOU 窗口，所以每次访问前都要重查，不能信任上一次的结果。

**问：为什么路径校验失败时不把真实路径告诉模型？**

路径信息对模型解决问题没有帮助，但对攻击者有用：逐个试名字，根据「路径不安全」和「不存在」这两种回答的差别，就能反推出目录结构。错误信息只给稳定的错误码和一句「换一个」。
