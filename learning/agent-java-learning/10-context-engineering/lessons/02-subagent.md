# 第 2 课：子 Agent 与委派边界

## 这一课解决什么

第 1 课让主 Agent 记住自己要干什么，但它没有减少**探索过程本身**产生的上下文。

让一个 Agent 去追一个深调用链里的 bug：它读文件、搜符号、跑命令，几十轮工具结果很快把历史塞满。计划还在，可主 Agent 现在要同时记住最初目标、当前计划，**以及一大段和最终结论无关的探索轨迹**。

子 Agent 的思路是：这段探索根本不该进主对话。

```text
父 Agent
  assistant: task(description="查清本项目用的测试框架")
        │
        ▼
  子 Agent（全新历史）
    system: 只做这一件事，给出有证据的结论，不要再委派
    user:   查清本项目用的测试框架
    ...三十轮读文件、搜索、跑命令...
        │
        ▼
父 Agent
  tool: "JUnit 5。证据：pom.xml 里 junit-jupiter 5.8.2"   ← 只有这一句
```

中间那三十轮留在子 Agent 的边界里，随它一起消失。父 Agent 只为一句结论付 token。

## 一、隔离的只有消息历史

这是本课最容易误读的地方，也是八条边界里五条在守的那句话。

| 东西 | 父子关系 | 为什么 |
| --- | --- | --- |
| 消息历史 | **隔离** | 本课存在的理由 |
| `ModelClient` | **隔离**（每次新建） | 共享实例会让两次委派的响应队列、重试计数互相污染 |
| `ToolRegistry` | **隔离**（每次新建） | 共享会让一个子任务注册的工具泄漏给下一个 |
| `ToolContext` | **共享** | 换身份等于审计断链 |
| `HookRegistry` | **共享** | 脱敏、审计这类横切规则不能因为换了层循环就失效 |
| `PermissionPolicy` | **共享** | 见第三节 |

父子跑在同一个 JVM、同一个进程、同一份权限策略；子 Agent 写下的副作用**会保留**。

**它不是沙箱。** 它解决的是上下文污染，不提供任何系统级隔离。把它当沙箱用是这一课最危险的误读。

## 二、为什么用工厂而不是实例

`ModelClientFactory` 和 `ToolRegistryFactory` 这两个接口只有一个方法，看着像过度设计。它们存在是因为**每次委派都要一个真正从零开始的子 Agent**。

传实例进来的话，两次委派共享同一个对象：测试里用 `FakeModelClient` 排响应队列时，第二次委派会接着读第一次剩下的队列；生产里如果客户端带连接状态、重试计数或熔断器状态，问题一模一样。

历史隔离靠新建循环，依赖隔离靠工厂。少任何一半，子 Agent 都不是真的从零开始。

`shouldCreateFreshDependenciesPerTask` 用 `assertNotSame` 把这条钉住。

## 三、权限必须共享，否则 task 就是提权路径

如果子 Agent 能拿到一份更宽松的策略，「委派」就成了绕过裁决的通道：父 Agent 删不掉受保护设备，但它可以派一个子 Agent 去删。

这不是理论风险 —— 提示词注入的标准手法就是让模型「换个身份再试一次」。

所以子 Agent 的权限**不会比父 Agent 更宽**。它也不会更窄：本课不做分级授权，那需要「按委派深度收紧策略」的机制，是另一个话题。

`shouldShareParentPermissionPolicy` 断言两件事：被拒的 handler 一次都没执行，**而且**留下了审计记录。后半句同样重要 —— 子 Agent 的操作要可追溯，否则「谁干的」在委派这一层就断了。

## 四、hooks 不许传 null，policy 可以

两个字段都是治理边界，但「没配」这件事的含义不同。

`policy` 为 null 表示「本次不启用权限系统」，语义明确。而 `hooks` 为 null 读起来像「子 Agent 不受 Hook 管」—— 恰好是本课要否定的那句话。

父 Agent 没有 Hook 时应当传一个空的 `HookRegistry`：那表达的是「受 Hook 管，只是当前没有规则」。和「不受管」是两件事。

这条不是洁癖。构造参数的类型约束是**读代码的人**唯一能看到的意图声明，允许 null 就等于在文档之外留了一个反例。

## 五、递归委派的两道防线

1. **提示词**：职责提示里写明「不要再委派」。软约束 —— 模型可以不听。
2. **注册表**：子 Agent 的注册表里**根本没有** `task`。它想调也调不到。

为什么两道都要：只靠提示词，遇到提示词注入就失效；只靠注册表，模型会反复尝试委派、浪费轮数。前者省 token，后者兜底 —— **而兜底那道才是真正生效的那道。**

还有第三道，针对的不是模型而是**写代码的人**：`runTask` 每次都检查工厂产出的注册表里有没有 `task`，有就直接报配置错误。一个图省事的 `toolsFactory` 直接返回父 Agent 的注册表，递归委派就复活了。

`shouldRejectRecursiveDelegation` 额外断言 `fake.getCallCount() == 0`：拦在建循环之前，不是等它跑起来再拦。

## 六、轮数上限只能收紧

`task` 是**同步**调用，父 Agent 在等它。子 Agent 一直调工具不收尾的话，父 Agent 就一直卡着，而父 Agent 自己的轮数上限在这期间**一轮都没走** —— 一次委派就能把整个请求拖到超时。

所以有 `MAX_SUBAGENT_ROUNDS = 30`，而且构造时只允许调小不允许调大。允许调用方放大等于允许它把闸门抬到任意高度，那这个闸门就不存在了。

## 七、失败结果不回传最后一条工具结果

只有 `FINAL_ANSWER` 算成功，其余全部归成错误。关键在于**轮数耗尽时不回传子 Agent 最后那条工具结果**。

那条工具结果通常看着像个正常答案。把它当结论回传，父 Agent 会以为子任务成功了 —— 它没有任何办法分辨「做完了」和「没做完但最后一步的输出恰好像结论」。

同理，子 Agent 内部抛异常时**不把 `e.getMessage()` 放进结果**。异常文本可能带内部路径、SQL、配置键名，它进了父上下文就等于进了模型可见范围，而模型下一轮可能把它复述给用户。`shouldSanitizeChildFailure` 用一个含 jdbc 连接串的异常把这条钉住。

## 八、Java 特有的一笔：线程池要关

`HookedAgentLoop` 内部有 `ToolTimeoutGuard`，它持有一个线程池。`runTask` 的 `finally` 里必须 `shutdown()`。

不关的话，**每次委派泄漏一个线程池**。教材是 Node 单线程模型，没有这个问题 —— 照抄会漏掉这一句，而这种泄漏在测试里看不出来，要跑够多次委派才会耗尽资源。

## 九、副作用等级：教材的 external 在 Java 侧怎么落

教材给 `task` 标的是 `external`。Java 侧 `ToolEffect` 只有 READ/WRITE/DESTRUCTIVE 三档，取 **WRITE**：

- 不是 READ —— 子 Agent 能写文件；
- 不是 DESTRUCTIVE —— 标成它会让**每一次**委派都弹确认框，这个机制就没人用了。

真正不可逆的部分由子 Agent 自己调的那些工具承担，而它们各自都要过同一套裁决。权限策略是共享的，拦得住。

这和第 1 课 `todo_write` 取 WRITE 是同一条规则的第二次应用：**副作用等级按撤销的真实成本定，不按听起来危险不危险定。**

## 常见面试题

**问：多 Agent 架构解决什么问题？什么时候不该用？**

它解决的是上下文污染：一段多轮探索的中间产物对最终结论没有价值，却要一直占着主对话的预算。适合「过程长、结论短、自包含」的任务。

不该用的场景：任务需要主对话的上下文才说得清（子 Agent 看不到父对话）；任务很短（一次委派的固定开销比省下来的多）；需要和用户来回确认（子 Agent 没有和用户对话的通道）。

**问：子 Agent 应该继承父 Agent 的权限吗？**

必须继承，而且不能更宽。否则委派就成了提权路径 —— 模型把想做的事包装成一次委派即可绕过全部裁决，这正是提示词注入会去找的缺口。更窄是合理的（分级授权），但那需要「按深度收紧」的机制，不是默认行为。

**问：怎么防止 Agent 无限递归地派生子 Agent？**

两道防线。提示词里说「不要再委派」是软约束，模型可以不听；真正生效的是子 Agent 的工具注册表里根本没有 `task`。再加一道针对开发者的检查：如果 `toolsFactory` 返回的注册表里含 `task`，直接报配置错误 —— 因为最可能打开这个洞的不是模型，是图省事直接复用父注册表的人。

**问：子 Agent 失败了，父 Agent 应该收到什么？**

一条结构化的错误，带错误码，不带内部细节。两个坑：一是别把子 Agent 最后一条工具结果当结论回传，父 Agent 分辨不出那是「做完了」还是「没做完」；二是别把异常文本回传，里面可能有路径、SQL、配置键名，进了父上下文就等于进了模型可见范围。

**问：同步委派有什么风险？**

父 Agent 在等的这段时间里，它自己的轮数上限一轮都没走。子 Agent 不收尾，整个请求就被拖到超时。所以子 Agent 必须有独立的轮数上限和工具超时，而且上限只能收紧不能放宽 —— 一个可以被调用方抬高的闸门等于没有闸门。
