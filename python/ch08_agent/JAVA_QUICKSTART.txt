第 1 步：理解压缩动机（10 分钟）
---------------------------------
为什么需要上下文压缩？
  问题：模型上下文窗口有限（如 128K tokens）
  场景：长对话历史超出限制 → API 报错
  影响：大工具结果占用过多 → 成本高、延迟大

Java 类比：类似缓存管理，LRU 淘汰旧数据

核心矛盾：
  - 模型需要完整历史才能理解上下文
  - 但完整历史会超出 token 限制
  - 必须智能压缩，保留关键信息


第 2 步：读核心实现（20 分钟）
---------------------------------
打开 features/compaction.py，按顺序阅读：
  1. CompactionManager 类 → 压缩管理器（类似 Spring Service）
  2. MessageGroup 概念 → 不可拆分的消息组
  3. ArtifactStore 类 → 大结果归档器（类似 FileRepository）
  4. ModelHistorySummarizer → 调用模型总结旧消息

重点理解：
  - RequestHistoryProcessor 接口 → 请求前处理
  - ToolResultProcessor 接口 → 结果后处理
  - Protocol = interface
  - dataclass = record

核心概念速记
---------------------------------
压缩动机 = 模型上下文有限 + 长对话超限 + 成本延迟问题

MessageGroup = assistant + tool_calls 配对，不可拆分（API 协议要求）

响应式压缩 = 超限后触发（reactive）
主动式压缩 = 提前预防超限（proactive，更平滑）

ArtifactStore = 大结果写磁盘，消息保留引用 ID，按需读取

字节数 vs 字符数 = UTF-8 编码更准确（中文 1 字符 = 3 字节）

两个接口 = RequestHistoryProcessor（请求前）+ ToolResultProcessor（结果后）

常见问题 FAQ
---------------------------------
Q: 压缩会丢失信息吗？
A: 会。旧消息被总结成摘要，细节会丢失。但 system prompt 和最近消息完整保留。

Q: 什么时候触发压缩？
A: 响应式：超过阈值后触发；主动式：接近阈值时提前触发。

Q: MessageGroup 为什么不能拆分？
A: OpenAI API 协议要求每个 tool_call 必须有配对结果，拆分会 400 错误。

Q: 大结果归档后如何读取？
A: 消息保留 artifact:// 引用，模型需要时可以调工具读取。

Q: 为什么用字节数不用字符数？
A: 模型按 token 计费，中文字符占多字节，字节数更接近真实 token 数。

Q: CompactionManager 实现了哪些接口？
A: RequestHistoryProcessor（请求前处理历史）+ ToolResultProcessor（结果后处理）。

Q: 压缩会影响模型效果吗？
A: 会。旧消息被总结，模型看不到完整细节。但保留最近消息，影响有限。

Q: 能否自定义压缩策略？
A: 可以。实现 RequestHistoryProcessor 和 ToolResultProcessor 接口即可。
