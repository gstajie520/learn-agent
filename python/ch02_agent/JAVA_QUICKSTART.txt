核心概念速记
---------------------------------
章节配置白名单 = 通过 is 身份验证防止伪造配置 DTO

命令执行边界 = CommandRunner 接口隔离 subprocess 细节

文件系统边界 = WorkspaceFileSystem 接口 + 5 种领域异常

工具注册表快照 = 确保模型看到的工具和实际能执行的工具一致

参数严格校验 = 拒绝多余字段，防止注入攻击

路径安全检查 = 禁止 ../ 和绝对路径，防止目录遍历

授权器 fail-closed 原则 = 授权系统故障时默认拒绝（安全优先）


常见问题 FAQ
---------------------------------
Q1: 为什么需要 ChapterProfile，不能直接用 int 章节号？
A1: Profile 是能力白名单，显式声明每章的功能边界。用 is 身份验证
    防止调用方伪造配置 DTO（内容相同但不是预定义常量的对象会被拒绝）。
    类似 Java 中只接受 enum 常量，不接受 new Enum(相同值)。

Q2: Protocol 和 Java interface 有什么区别？
A2: Protocol 是 Python 的结构化类型（structural typing），不需要显式继承。
    只要实现了对应方法就满足契约，类似 Go 的 interface。
    Java interface 是名义类型（nominal typing），必须显式 implements。

Q3: 为什么 build_agent 要检查 `profile is P01 or profile is P02`？
A3: 防止调用方创建 ChapterProfile(2, P02.capabilities) 这样内容相同
    但不是预定义常量的对象。`is` 比较对象身份（内存地址），不是字段值。
    这确保只能传入模块定义的固定常量，类似单例模式的安全检查。

Q4: 第 2 章和第 1 章的核心区别是什么？
A4: 三个关键变化：
    - 新增章节配置白名单机制（profiles.py）
    - 抽象命令执行和文件系统为接口（commands.py + filesystem.py）
    - 增加四个文件工具（read_file、write_file、edit_file、glob）
    核心循环逻辑（loop.py）基本保持不变。

Q5: 为什么工具参数校验要拒绝多余字段（additionalProperties: False）？
A5: 防止注入攻击和意外副作用。如果允许多余字段，恶意模型可能传入
    {"path":"x","__proto__":...} 或 {"path":"x","sudo":true} 等危险参数。
    严格校验确保只处理定义好的字段，避免参数污染。

Q6: 路径安全检查具体做了什么？
A6: WorkspaceFileSystem 确保所有路径：
    - 必须是相对路径（不允许 /etc/passwd 或 C:\Windows）
    - 解析后不能逃出工作区（禁止 ../../../etc/passwd）
    - 最终绝对路径必须在 workspace 目录树下
    类似 Java 中的 Path.normalize() + startsWith() 检查。

Q7: 为什么授权器异常要默认拒绝（fail-closed）？
A7: 安全系统设计原则：宁可误拒绝（假阴性），不可误通过（假阳性）。
    如果授权器崩溃或抛异常时默认允许，攻击者可以故意触发异常来绕过授权。
    loop.py:198-200 的 except Exception 确保任何授权失败都转为拒绝结果。
