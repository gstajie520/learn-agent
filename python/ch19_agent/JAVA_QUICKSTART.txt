第 1 步：理解事件协议（10 分钟）
---------------------------------
打开 core/events.py，理解事件接口和队列：
  RuntimeEvent 接口：event_id、context_identity、idempotency_key、to_payload
  EventInbox 队列：publish、drain、wait
  runtime_event_message：包装成 user 消息

Java 类比：
  RuntimeEvent = interface Event { String getId(); Map<String,Object> toPayload(); }
  EventInbox = BlockingQueue<RuntimeEvent> + Condition
  deque = ArrayDeque（双端队列）


第 2 步：读主循环集成（20 分钟）
---------------------------------
打开 core/loop.py，按顺序阅读：
  1. run_events() 入口                → 消费一条事件（行 256-296）
  2. _inject_runtime_events()         → 批量注入事件（行 518-536）
  3. _pending_event_acks 字段         → ack 失败重试（行 231、258-262）

重点理解：
  - 事件在两个安全点注入：循环开始前、模型返回文本后
  - 事件包装成 user 消息，不伪装成 tool 消息
  - ack 失败时保留租约，下次只重试确认

核心概念速记
---------------------------------
事件驱动 = 后台线程发布事件 → 队列缓冲 → 主循环在安全点注入

为什么是 user 消息 = 事件是外部输入，不是工具结果，保持消息配对完整性

ack 机制 = 处理成功后确认，失败时保留租约，防止事件丢失

幂等性 = event_id 去重 + idempotency_key，保证每个事件只处理一次

context_identity = 区分系统事件（随时注入）和用户事件（只在该用户回合注入）

EventInbox = 线程安全队列，用 Condition 实现阻塞等待

常见问题速查
---------------------------------
Q: 为什么事件不是 tool 消息？
A: 事件是外部输入，不是 Agent 主动调用工具的结果，伪装会破坏消息配对

Q: 为什么需要 EventInbox？
A: 后台线程不能直接修改历史（线程安全），队列保证 FIFO 顺序和同步

Q: ack 失败后会发生什么？
A: 保留到 _pending_event_acks，下次 run_events 只重试 ack，不重复处理

Q: _seen_event_ids 的作用？
A: 去重。重启后可能重新消费未 ack 事件，通过 event_id 保证幂等性

Q: 为什么 deque 而不是 list？
A: deque.popleft() 是 O(1)，list.pop(0) 是 O(n)，且天然支持 FIFO

Q: context_identity 为什么影响注入时机？
A: 系统事件随时注入，用户上下文事件只在该用户回合注入，防止上下文混淆
