第 2 步：读组合根装配逻辑（20 分钟）
---------------------------------
打开 bootstrap.py，按顺序阅读：
  1. _full_harness_runtime_status 函数  → 运行态状态汇总
  2. build_agent 函数开头               → profile 对象身份校验

重点理解：
  - profile_for_chapter(profile.chapter) is not profile
    → 只接受固定单例，拒绝临时构造的冒充对象（类似只接受 enum 常量）

  - "capability" in profile.capabilities
    → 能力白名单判断，每章只启用档案允许的能力

  - task_store is not worktree_runtime.store
    → 对象身份校验，保证跨能力对象共享同一实例

  - lambda: _full_harness_runtime_status(...)
    → 捕获运行时引用，每轮重新读取状态而非构建期快照

四条核心不变量（必须理解）
---------------------------------
不变量 1：动态工具的可见时机
  - 一次模型回复只使用一个 ToolRegistry 快照
  - MCP 连接成功后动态工具下一轮才可见
  - 本轮快照被密封，即使工具已发布也不能调用

不变量 2：消息配对契约
  - 每个 tool_call 必须恰好配一个同 ID 的 tool result
  - 一个成功一个失败不影响配对
  - 违反配对会导致模型 API 拒绝请求

不变量 3：授权硬边界
  - Prompt 只负责提示，不是授权依据
  - PermissionPolicy 的 write_boundary 硬拒绝越界写入
  - 审批器放行不等于放行越界（第 4.3 节不变量）

不变量 4：资源逆序关闭
  - 成功时 Runner 持有 resources，统一逆序关闭
  - 失败时 closables 兜底，按创建顺序逆序关闭
  - 任何路径都不遗留 stdio 子进程或后台线程

为什么这样设计？（设计动机速查）
---------------------------------
Q: 为什么用增量表而不是逐章手写能力集合？
A: 因为"第 N 章是第 N-1 章的严格超集"由数据结构保证，而不是靠人工核对 20 个 frozenset。

Q: 为什么用对象身份（is）而不是类型校验？
A: 因为调用方不能临时构造一个同字段 ChapterProfile 来冒充正式章节，类似只接受 enum 常量。

Q: 为什么 status_provider 是 lambda 而不是构建期快照？
A: 因为 lambda 捕获运行时引用，每轮读到的都是当前状态，MCP 连接变化才能在下一轮体现。

Q: 为什么 runtime_status 固定在 Prompt 最后？
A: 因为状态变化不移动、不重排前面的稳定段落，缓存键的 identity/tools/workspace 不会失效。

Q: 为什么资源关闭有两条路径？
A: 因为 build_agent 本身可能失败。成功时 Runner 统一关闭，失败时 closables 兜底，都保证回收。

Q: 为什么 Worktree、WorkStealing、TaskStore 必须共享？
A: 因为它们操作同一份任务状态。不共享会导致 Lead 和 Teammate 看到的任务图分叉。


面试常考点
---------------------------------
1. P20 新增了哪些独立运行时？
   答：零个。full_harness 是验收标记能力，不新增独立运行时。

2. 增量表如何保证超集关系？
   答：accumulated.extend(delta) 只追加不删除，下一轮天然包含所有历史能力。

3. 为什么 build_agent 拒绝能力越级注入？
   答：因为低章节没有对应的测试覆盖，绕过渐进校验可能暴露未测组合。

4. runtime_status 和 typed event 的区别？
   答：event 是主动推送进历史，status 是每轮重新读取给模型决策提示。

5. 为什么 closables 是逆创建顺序？
   答：因为后创建的对象可能依赖先创建的对象，逆序关闭保证依赖安全。
