第 1 步：从测试看目标（10 分钟）
---------------------------------
打开 tests/test_ch18_worktrees.py，理解 Worktree 的三个核心场景：
  场景1：创建 Worktree → claim 任务 → 路由到独立目录
  场景2：失效 token 不能回退到主目录（安全边界）
  场景3：删除前必须完成任务（前置条件）

Java 类比：先读 WorktreeServiceTest 理解业务需求


第 2 步：读领域模型和核心服务（20 分钟）
---------------------------------
打开 features/worktrees.py，按顺序阅读：
  1. WorktreeBinding        → 不可变状态快照（类似 record）
  2. WorktreeRuntime.__init__ → 依赖注入（类似 Spring）
  3. create_worktree        → 两阶段提交（reserve → active）
  4. resolve                → claim token 路由到可信 cwd
  5. remove_worktree        → 多重安全检查

重点理解：
  - WorktreeBinding = 不可变 record
  - WorktreeStore = Repository interface
  - status 五态 = 状态机枚举
  - resolve = 请求拦截器（每次工具调用前执行）

---------------------------------
快速浏览两个集成点：

不要深入细节，理解两个核心点就行：
  1. 状态变更和审计事件在同一 SQLite 事务
  2. 每次工具执行前都重新验证 claim token


核心概念速记
---------------------------------
Worktree 隔离 = 每个任务独立目录 + 独立分支 → 并发不覆盖

两阶段提交 = reserve 预留名称 → Git 成功后 active

claim token 路由 = token → task_id → WorktreeBinding → 可信 cwd

Fail-Safe 删除 = 先证明安全（任务完成+Git干净+已合并）→ 任何失败转 needs_review

状态机五态 = reserved → active → kept/needs_review/removed

路径安全规则 = branch 固定 wt/{name}，路径固定 .agent_tutorial/worktrees/{name}

常见陷阱和误区
---------------------------------
❌ 误区1：以为 branch 和 path 可以自由命名
   ✓ 真相：固定规则防止注入，模型不能传任意值

❌ 误区2：以为删除失败应该直接报错
   ✓ 真相：转 needs_review 保留现场，保护用户数据优先

❌ 误区3：以为 resolve 只需调用一次
   ✓ 真相：每次工具调用前都要重新验证 token 有效性

❌ 误区4：以为 Git stderr 应该返回给模型
   ✓ 真相：stderr 不稳定，领域层返回稳定中文错误


Java 开发者常问问题
---------------------------------
Q: WorktreeBinding 为什么是不可变的？
A: 类似 record，状态变更由 Repository 生成新快照，确保审计追踪

Q: 为什么不用 ORM 而用原生 SQL？
A: 事务边界明确，状态迁移+审计事件原子性由 SQL 事务保证

Q: 状态机转换如何防止非法跳转？
A: _transition_worktree 检查 action 合法性，类似状态模式

Q: 如何防止并发修改冲突？
A: SQLite 事务隔离 + WHERE status = ? 条件更新

Q: 为什么 Git 操作不在 Repository 层？
A: Git 是基础设施，通过 GitRunner 接口注入，便于测试替换
