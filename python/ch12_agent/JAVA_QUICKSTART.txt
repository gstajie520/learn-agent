Java Developer 3-Step Quick Guide to Task DAG (45 minutes)
===============================================

Step 1: Understand the Domain Model (10 minutes)
---------------------------------
Open features/tasks.py and understand the core entities:
  - Task: Immutable record with id, subject, description, status, owner, blocked_by, timestamps
  - TaskStore: Repository interface (create, list_all, get, claim, complete)
  - Five tool definitions: create_task, list_tasks, claim_task, complete_task, get_task

Java analogy: Read the domain model first like @Entity and Repository interface

Key differences from TODO:
  - TODO: Session-local step list, lost on process exit
  - Task: Workspace-level project state, persisted to disk
  - Task supports DAG dependencies (blocked_by), TODO is just a sequence


Step 2: Understand the Persistence Mechanism (20 minutes)
---------------------------------
Open adapters/task_json.py and read in order:
  1. JsonTaskStore.__init__     -> File path and lock initialization
  2. JsonTaskStore.create        -> Create task with DAG validation
  3. JsonTaskStore._validate_graph -> Check for missing edges, self-deps, cycles
  4. JsonTaskStore._detect_cycles  -> DFS-based cycle detection
  5. JsonTaskStore._atomic_write   -> write temp + rename pattern

Key concepts:
  - File lock: fcntl.flock (POSIX) or msvcrt.locking (Windows)
  - Atomic write: tmp file + rename (filesystem atomic operation)
  - DAG validation: Detect cycles, missing dependencies, self-dependencies
  - State machine: pending -> in_progress (claim) -> completed (complete)

Core Concepts Quick Reference
---------------------------------
Task DAG = Directed Acyclic Graph of workspace tasks with dependency tracking

State Machine = pending -> (claim) -> in_progress -> (complete) -> completed

Atomic Write = write to tmp file + rename (filesystem atomic op) -> prevents corruption

File Lock = Process-level lock (fcntl/msvcrt) -> serializes concurrent access

Cycle Detection = DFS with visited set + recursion stack -> prevents deadlock

Repository Pattern = TaskStore interface + JsonTaskStore impl -> swappable storage


Why These Design Choices?
---------------------------------
Q: Why not directly modify JSON without file lock?
A: Concurrent writes would corrupt the file (race condition)

Q: Why use tmp + rename instead of direct write?
A: Direct write is not atomic; crash mid-write leaves invalid JSON

Q: Why check for cycles on every create/complete?
A: Prevents A depends on B, B depends on A -> deadlock

Q: Why must Task go through claim before complete?
A: Ownership tracking (who is working on this) prevents duplicate work

Q: Why TaskStore interface instead of direct JsonTaskStore?
A: Dependency Inversion Principle -> can swap to SQLite/Redis later
